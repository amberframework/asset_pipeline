# Agent DX Accessibility Gap Analysis

This analysis captures what the Frontloader Studio demo needed in order to be
accessible, polished, and verifiable, then separates what is already reusable
from what still lives as demo-specific craft. The goal is to make future agents
able to install Asset Pipeline and generate accessible design-system views without
reverse engineering the demo.

Inputs for this pass:

- Local inspection of components, renderer output, JavaScript helpers, docs, and
  validation scripts.
- Companion audits for accessibility, component/API gaps, agent onboarding, and
  validation feedback.
- External Claude adversarial planning review.

## Executive Summary

The milestone proof is accessible because the team built a strong shell around
the generated pages: hand-authored semantic markup, a large vanilla helper file,
demo-specific components, and demo-specific audit scripts. That proves the
direction, but the durable library API does not yet make the same outcome cheap,
easy, and high quality across future web, desktop, mobile, and native compile
targets.

The next phase should move those guarantees inward:

- Continue moving canonical design-system components out of
  `Components::Examples` implementations after the generic namespace bridge.
- Make behavior hooks and accessibility contracts explicit component metadata.
- Convert demo validation into reusable app validation.
- Provide downstream `AGENTS.md` / `CLAUDE.md` instructions and templates.
- Add fast compile/spec/static feedback before browser evidence capture.
- Keep the rendered demo visually stable while the demo generator shrinks.
- Keep component names generic so the same concepts can map cleanly across web,
  desktop, mobile, and future native targets.

## What Was Necessary But Not Standard Yet

### 1. Accessible Behavior Lives In One Demo Runtime

`public/js/design-system.js` contains the behavior that made the demo work, with
`public/js/amber-design-system.js` kept as a compatibility copy:

- Theme toggle and explicit light/dark state.
- Disclosure state and `aria-expanded`.
- Dialog open/close, focus trap, and return focus.
- Row filtering with live status.
- Dynamic field errors with `aria-invalid` and `aria-describedby`.
- Password policy feedback.
- Luhn and expiry validation.
- Payment formatting and promo status.
- Live search and chat updates.
- Command palette keyboard behavior.
- Tabs roving focus and panel hiding.
- Carousel status and keyboard controls.
- Timeline reveal and reduced-motion handling.

Gap: this file is not a modular shipped runtime, not auto-mounted by the shard,
and not driven by component behavior manifests. Several helpers still embed demo
copy or demo data, such as pricing math, search records, chat author labels, and
theme labels.

Needed API:

- `Components::DesignSystem::BehaviorRegistry`
- `component.behavior(:tabs)` / `component.behavior(:dialog)`
- Neutral `data-ap-*` hook contracts generated by components, with current
  `data-amber-*` aliases preserved during alpha migration
- Runtime modules under `assets/js/design-system/`
- Integration helper such as
  `Components::Integration.design_system_script_tag`

### 2. Canonical Components Are Still Partly Backed By Examples

The promoted API surface is now available through generic
`Components::DesignSystem::*` aliases, and the canonical demo uses those names.
Several aliases are still backed by implementation classes under
`src/components/examples/*`.

Gap: downstream agents now have the right namespace, but the implementation
files and some compatibility specs still carry `Examples` names. Agents may
still copy the older reactive examples if the docs are not explicit.

Available generic API:

- `Components::DesignSystem::Button`
- `Components::DesignSystem::Card`
- `Components::DesignSystem::FormField`
- `Components::DesignSystem::AuthForm`
- `Components::DesignSystem::PaymentForm`
- `Components::DesignSystem::PricingCard`
- `Components::DesignSystem::DataTable`
- `Components::DesignSystem::SimpleChart`
- `Components::DesignSystem::ScheduleHeatmap`
- `Components::DesignSystem::Timeline`
- `Components::DesignSystem::Dialog`
- `Components::DesignSystem::Tabs`
- `Components::DesignSystem::CommandPalette`
- `Components::DesignSystem::Carousel`
- `Components::DesignSystem::ThemeSwitcher`

Still needed:

- Move promoted implementations out of `src/components/examples/*` when the
  compatibility window closes.
- Add vanilla no-build `Chat`, `LiveSearch`, and richer communication wrappers
  before promoting those concepts. The old reactive examples are not canonical.
- Keep `Components::Examples::*` as compatibility aliases during alpha
  migration.

### 3. Form Semantics Are Proven, Not Productized

The demo uses good browser-native form semantics: `type="email"`,
`autocomplete`, `required`, `minlength`, `pattern`, `inputmode`, password
confirmation, Luhn validation, future-expiry validation, visible errors, and
status regions.

Gap: the reusable `FormField` owns static label/control/error markup and
`Fieldset` now owns native grouping, but runtime validation, password policy,
payment-specific rules, and status updates still live in the standalone
JavaScript helper. `PaymentForm` and `AuthForm` still hard-code field ids and
copy.

Needed API:

- `Fieldset`
- `ValidatedForm`
- `FormField`
- `FormStatus`
- `FieldError`
- `ValidationRule`
- `PasswordPolicy`
- `PaymentCardFieldSet`
- Id-prefixing for every reusable form field group
- One source of truth that renders native HTML attributes and JS validation
  config from the same rule definition

### 4. Renderer Output Does Not Fully Delegate To Canonical Primitives

`UI::Web::Renderer` injects the current token set and maps some controls to `am-*`
classes, but many paths still hand-build roles, inline styles, and behaviorless
markup.

Gap: a view rendered through the web renderer can diverge from the accessibility
and behavior contracts proven by the canonical components.

Needed API:

- Renderer adapter layer that maps UI views through canonical canonical primitives.
- Shared output for button, card, field, segmented control, tabs, dialog,
  disclosure, picker/select, progress, live region, and alert.
- Renderer tests that assert accessible names, roles, focus states, and token
  cascade behavior.

### 5. Accessibility Helpers Are Private Conventions

The demo needed focus trapping, focusable discovery, roving focus, disclosure
state, return focus, live regions, source-data table fallbacks, visually hidden
content, and accessible chart/heatmap summaries.

Gap: these are hidden in JS or duplicated as component-local CSS/string markup.

Needed API:

- `Accessibility::FocusTrap`
- `Accessibility::RovingFocusGroup`
- `Accessibility::DisclosureState`
- `Accessibility::LiveRegion`
- `Accessibility::AccessibleName`
- `Accessibility::VisuallyHidden`
- `Accessibility::SourceDataTable`
- `Accessibility::DataVizFallback`

### 6. Validation Is Strong But Demo-Locked

Current validation is valuable:

- Static page checks.
- Forbidden-class audit for Bootstrap-shaped output.
- CDP browser audit.
- Accessibility-tree snapshots.
- Keyboard traversal.
- Touch target checks.
- Contrast sampling.
- Reduced-motion checks.
- Axe and IBM Equal Access.
- Screenshot matrix.

Gap: the first manifest-driven static validator now exists as
`scripts/validate_design_system_manifest.cr`, with the current demo represented
by `docs/web-design-system/web-demo.routes.yml`. The browser, screenshot, axe,
IBM, keyboard, contrast, and interaction-flow scripts still hard-code the seven
Frontloader pages, page copy, selectors, and interaction flows.

Needed API:

- `asset_pipeline validate --fast`
- `asset_pipeline validate --static`, backed initially by
  `scripts/validate_design_system_manifest.cr`
- `asset_pipeline validate --browser`
- `asset_pipeline validate --a11y`
- `asset_pipeline validate --full`
- `asset_pipeline capture`
- `design-system.routes.yml` page/flow manifest. The first static shape is
  captured in `docs/web-design-system/web-demo.routes.yml` and
  `templates/design-system/design-system.routes.yml`.
- `ComponentAuditManifest` generated from component contracts
- Shared CDP browser harness used by screenshot, axe, IBM, keyboard, contrast,
  reflow, and accessibility-tree checks

### 7. Agent Instructions Are Not Yet Installable

The repo has detailed docs, but downstream agents need operational instructions
that travel with the installed shard. Current `CLAUDE.md` mixes older
Stimulus/import-map guidance, native-platform guidance, and the new web design
system. The root guidance has been reconciled to say that legacy FrontLoader can
still support Stimulus integration, while design-system web helpers are
vanilla JavaScript only.

Gap: an agent installing the library does not have a single short playbook that
answers what to require, what components to use, what patterns are forbidden,
and what command ladder to run.

Needed artifacts:

- Root `AGENTS.md` for this repo.
- `templates/design-system/AGENTS.md` for consuming apps.
- `templates/design-system/CLAUDE.md` for consuming apps that use Claude Code.
- `docs/web-design-system/agent-playbook.md`.
- `docs/web-design-system/accessibility-contract.md`.
- `docs/web-design-system/generated-view-conventions.md`.
- `docs/web-design-system/component-api.md`.
- `docs/web-design-system/forbidden-patterns.md`.

### 8. Fast Feedback Is Missing

Agents need quick diagnostics before running a full browser matrix.

Gap: there is no Crystal LSP integration documented for this project and no
design-system compile-check harness. Reusable accessibility matchers for
rendered HTML snippets now exist in `spec/support/accessibility_matchers.cr`,
but they are not yet packaged as consuming-app helpers.

Needed feedback loop:

- `crystal build --no-codegen` or focused `crystal spec` harness for generated
  views.
- Package `spec/support/accessibility_matchers.cr` for downstream apps or move
  the helper assertions into a public test-support shard path.
- `spec/support/render_helpers.cr`.
- `make agent-check` or `scripts/design_system_agent_check.cr`.
- Optional `crystalline` setup documentation if the team wants LSP-backed local
  editing.

## Reusable Today

- Semantic token model and light/dark CSS variable cascade.
- CSS generator accessibility baseline for focus, motion, and ARIA variants.
- `ComponentVariant` validation vocabulary.
- Generic `Components::DesignSystem::*` aliases for the current promoted proof
  components, backed by compatibility implementations where needed.
- `Button`, `Card`, `FormField`, chart fallback, and several promoted
  components as implementation seeds.
- Vanilla helper file as a behavior reference.
- Existing accessibility evidence scripts as reusable algorithm references.
- `component-contracts.md`, `component-catalog.md`, `visual-language.md`, and
  `evidence.md` as human-readable intent.

## Demo-Specific Today

- Frontloader Studio page copy and page manifest.
- `output/` page list and screenshot matrix.
- Hard-coded browser audit flows.
- Pricing calculator formula and live-search records.
- Page shell/nav/hero/panel/badge/alert/metric/sidebar/toast markup inside the
  demo generator.
- Browser/a11y audit lists that know the seven generated pages instead of
  reading a consuming app manifest.

## Library vs Docs vs CLI

| Concern | Home |
| --- | --- |
| Form fields, validation, dialogs, tabs, carousel, command palette, disclosure | Library Crystal API |
| Focus trap, roving focus, field errors, password rules, Luhn, reduced motion | Library JS runtime modules |
| Agent task recipes and forbidden patterns | Docs and templates |
| Page conventions and install instructions | Docs and downstream `AGENTS.md` |
| Landmark/label/ID/static semantic checks | Reusable CLI |
| Keyboard/contrast/AX/axe/IBM/screenshot evidence | Reusable CLI browser harness |
| Fast inner loop | Crystal spec helpers and compile-check harness |

## Highest-Leverage Next Move

Start with installable agent guidance and reusable validation contracts before
moving files. That creates the stable target for the API migration:

1. Ship `AGENTS.md` / downstream template instructions.
2. Document generated view conventions and forbidden patterns.
3. Define a manifest shape for pages, components, behaviors, and validation.
4. Promote components into a stable namespace.
5. Refactor validation scripts to consume the manifest.
