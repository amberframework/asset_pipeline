# Phase 6.5 — Audit-Infrastructure-First

**Tier:** N/A (infrastructure phase)
**Depends on:** Phases 1, 2, 3, 4, 5 (must observe a working multi-platform render)
**Blocks:** Phases 6, 7 (Phase 6 uses this harness during dev; Phase 7 wraps it into CI)
**Status:** Not Started (created 2026-05-22 from planning retrospective; brief authoring pending)

## Why this phase exists

Phase 3's retrospective documented 10 remediations the original plan didn't predict. The single most expensive cost driver — separately documented as **Principle 6** in `docs/initiative-cross-platform-ui/handoff/planning-retrospective-2026-05-22.md` — was that **audit infrastructure ran only at validation-gate time, not during implementation.** Bugs that empirical audit would have caught immediately (axe-core contrast violation, listitem ARIA violation, the entire reactivity gap) landed in commits and required separate remediation dispatches to fix.

The original master plan had Phase 7 (Accessibility & Visual Verification Automation) depending on Phase 6 (Side-by-Side Demo App). That ordering directly conflicts with the audit-first lesson — Phase 6 would have repeated Phase 3's pattern of "ship, then chase regressions surfaced at gate time."

Phase 6.5 inserts the audit infrastructure BEFORE Phase 6 begins. Phase 6's implementer uses Phase 6.5's harness during development. Phase 7 wraps Phase 6.5's harness into CI.

## Scope summary

In scope:

- **Visual diff baseline tooling.** Reusable Crystal harness that takes screenshots on macOS / iOS sim / web (CDP) / Android (deferred or stubbed), diffs against committed baselines, surfaces pixel-level regressions with tolerance.
- **CDP harness extensions.** Generalize `scripts/phase04_cdp_harness.cr` so it can drive any phase's web demos — focus trap probes, escape probes, ARIA inspection, axe-core + IBM Equal Access injection, screenshot capture with viewport / scheme controls.
- **AXTest pattern library.** Reusable patterns from `spec/ui/hig_validation/macos_*_spec.cr` extracted into a library that future specs `require` rather than copy.
- **XCUITest pattern library.** Same for `samples/cross_platform/ios_host/UITests/Phase03BehaviorTests.swift` patterns (focus trap, value-bound controls, sheet present/dismiss, dismiss reason capture).
- **Accessibility audit drivers.** Vendored axe-core + IBM Equal Access integration that any phase's web fallback / demo can run with one command.
- **Per-platform invariant probe runners — explicit coverage matrix.** Per the retrospective's per-platform probe menu (Section 5 of the Phase Brief Template), provide a Crystal entry point that takes an invariant ID + platform + slug and runs the appropriate probe. Phase 6.5 MUST ship runners for all 11 invariants × 4 platforms = 44 cells, with each cell being either (a) a working probe command, or (b) an explicit `skip` record with owner-approved date matching the schema. Currently-known skip candidates: Android cells for I-9 (embedding) and I-11 (build closure) per Phase 1 #17 architect precedent; web cells for I-9 (no embedding on web). Every other cell must be a real probe by end of Phase 6.5.

Out of scope:

- The Side-by-Side Demo App itself (that's Phase 6).
- GitHub Actions / CI workflow files (that's Phase 7).
- Android sim/emulator infrastructure (deferred — known gap from Phase 1 #17 architect adjudication; will be addressed when Android build closure is resolved separately).

## Acceptance summary

Phase 6.5 is done when:

- Any Implementer working on Phase 6 can run `crystal run scripts/audit_harness.cr -- --invariant I-3 --platform ios --slug <demo-slug>` and get a structured pass/fail result in < 60 seconds.
- Visual diff baselines for the existing Phase 3 + Phase 4 demos exist as committed PNGs and can be regenerated by `scripts/regenerate_baselines.sh`.
- A new Phase 6 demo screen can be added by authoring (a) a Crystal source file, (b) a slug entry in the existing slug-routing pattern, and (c) zero new harness infrastructure.
- Phase 7's CI workflow can call `scripts/audit_harness.cr` and `scripts/regenerate_baselines.sh` directly without modification.

Detailed checks in `validation.md` (to be authored once the brief is dispatched).

## Risk notes

- **Crystal Android cross-build remains unverified.** Phase 6.5 should not pretend to ship Android probes that haven't been demonstrated. Either ship them with real Android build proof, or declare Android probes as `skip` records with owner approval per the schema.
- **Visual baselining is appearance-sensitive.** macOS 26.5 + iOS 26.5 + Xcode 26.5 form the captured baseline; any toolchain upgrade invalidates baselines. The harness must capture the toolchain fingerprint per baseline.
- **TCC determinism on macOS test runners.** Phase 4 R2 saw macOS AXTest spec fail because TCC re-granting wasn't deterministic after rebuild. Phase 6.5 must either solve this or document the manual operator step per CI run.
